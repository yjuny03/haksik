# AI 신고 판단 신뢰도·구체화 계획서

## 1. 문서 목적

이 문서는 학식목장 AI 신고 자동 처리 기능이 어떤 근거로 콘텐츠를 판단하고, 어떤 경우에 자동 블라인드하며, 어떤 경우에 관리자 검토로 넘기는지를 이해하기 쉽게 설명한다.

현재 구현된 `MockAiClient`는 AI 자동 처리의 전체 흐름을 검증하기 위한 시뮬레이터다. 신고 접수, 분석 결과 저장, 정책 검증, 자동 블라인드, 관리자 확인, 처리 취소와 복구가 정상적으로 이어지는지를 검증하는 것이 현재 단계의 주목적이다.

현재 Mock 결과의 `riskScore`와 `confidenceScore`는 실제 데이터로 정확도를 측정해 보정한 값이 아니라 규칙별 고정값이다. 따라서 현재 결과를 실제 AI의 추론 정확도나 통계적 신뢰도로 표현해서는 안 된다.

최종 목표는 다음과 같다.

> AI가 콘텐츠의 의미와 문맥을 해석하고, 서버가 객관적인 증거와 서비스 정책을 검증하며, 애매한 결과는 관리자가 판단하는 구조를 만든다.

---

## 2. 현재 Mock 방식의 한계

현재 Mock은 특정 키워드와 정규식 패턴을 이용한다.

예를 들어 다음과 같은 단서를 확인한다.

- URL 포함 여부
- 제한된 광고 키워드
- 전화번호·이메일·주민등록번호 형태
- 같은 문구 또는 문자의 반복
- 사전에 정의한 욕설 표현
- 공격 대상 표현 존재 여부

이 방식은 결과가 일정하고 테스트하기 쉽지만, 사람이 문장의 전체 의미를 이해하는 것처럼 판단하지 못한다.

예시:

```text
3초 만에 끝나는 망고 타임특가, 오늘만 이 가격!
https://www.mango.com
```

사람은 다음 표현을 종합해 광고로 이해할 수 있다.

- `타임특가`: 구매 기회를 제한하여 행동을 유도
- `오늘만`: 긴급성을 강조
- `이 가격`: 가격 혜택을 강조
- 외부 쇼핑몰 URL: 서비스 밖으로 이동하도록 유도

하지만 Mock의 광고 키워드 목록에 `타임특가`, `오늘만`, `이 가격`이 없다면 이 문장을 `SAFE`로 판단할 수 있다. 이것은 자동 처리 구조의 문제가 아니라 Mock이 의미를 추론하지 못하는 한계다.

따라서 Mock 규칙을 계속 추가하는 것만으로는 모든 표현을 처리할 수 없다. 광고 문구, 신조어, 우회 욕설, 풍자, 인용처럼 표현이 계속 달라지는 영역은 실제 AI의 의미 추론이 필요하다.

## 3. 예시 문장에 대한 합리적인 판단

다음 문장은 광고 성격이 비교적 명확하다.

```text
3초 만에 끝나는 망고 타임특가, 오늘만 이 가격!
https://www.mango.com
```

그러나 광고라고 판단하는 것과 즉시 자동 블라인드해야 하는지는 별개의 문제다.

합리적인 초기 판정 예시는 다음과 같다.

```json
{
  "category": "SPAM_AD",
  "decision": "REVIEW_REQUIRED",
  "riskScore": 0.65,
  "confidenceScore": 0.94,
  "policyCodes": ["SPAM-COMMERCIAL"],
  "reasonSummary": "시간 제한과 가격 혜택을 강조하며 외부 상업 사이트 방문을 유도합니다."
}
```

판단 근거:

- 광고라는 사실은 비교적 명확하므로 `confidenceScore`는 높다.
- 정상 쇼핑몰 링크이며 한 번만 게시됐다면 즉각적인 피해 가능성은 피싱보다 낮으므로 `riskScore`는 중간 수준이다.
- 광고 여부는 확실하지만 자동 블라인드 기준인 높은 위험도에는 미달하므로 관리자 검토로 보낸다.

같은 문구를 짧은 시간 동안 여러 게시판에 반복했다면 판단이 달라진다.

```json
{
  "category": "SPAM_AD",
  "decision": "AUTO_HIDE",
  "riskScore": 0.92,
  "confidenceScore": 0.97,
  "policyCodes": ["SPAM-COMMERCIAL", "SPAM-REPEATED"]
}
```

반복 게시라는 객관적인 증거가 추가되면서 서비스 방해와 확산 가능성이 커지기 때문이다.

이 사례는 `riskScore`와 `confidenceScore`를 반드시 분리해야 하는 이유를 보여준다.

---

## 4. 두 점수의 차이

### 4.1 `riskScore`

`riskScore`는 콘텐츠가 서비스에 계속 노출될 때 발생할 수 있는 피해 가능성과 정책 위반 강도다.

판단 질문:

- 이용자에게 실제 피해가 발생할 수 있는가?
- 피해가 발생한다면 얼마나 심각한가?
- 서비스 이용을 얼마나 방해하는가?
- 빠르게 확산되거나 오래 남을 가능성이 있는가?
- 금전, 안전, 사생활, 존엄성에 직접적인 피해가 있는가?

`riskScore`가 올라가는 예:

- 정상 쇼핑몰 링크보다 피싱 링크
- 한 번 올린 광고보다 여러 게시판에 반복한 광고
- 일반 연락처보다 주민등록번호·계좌·상세 주소 노출
- 가벼운 불쾌 표현보다 특정인을 향한 심각한 인격 비하
- 단순 반복보다 대화를 사용할 수 없을 정도의 대량 도배

### 4.2 `confidenceScore`

`confidenceScore`는 AI가 선택한 유형과 위험도 판단이 맞다고 보는 확실성이다.

판단 질문:

- 위반 표현이 직접적으로 나타나는가?
- 특정 공격 대상이 명확한가?
- 앞뒤 문맥이 충분한가?
- 다른 정상적인 의미로 해석될 가능성이 적은가?
- 서버가 확인한 객관적 증거와 AI 판단이 일치하는가?
- 인용, 농담, 교육, 피해 신고일 가능성이 없는가?

`confidenceScore`가 낮아지는 예:

- 문장의 앞뒤가 잘림
- 공격 대상이 불명확함
- 욕설을 직접 사용한 것인지 인용한 것인지 알 수 없음
- 광고인지 정상적인 정보 공유인지 구분하기 어려움
- 숫자열이 전화번호인지 주문번호인지 알 수 없음
- AI와 서버 규칙의 결과가 서로 다름

### 4.3 두 점수를 평균 내면 안 되는 이유

다음 사례를 가정한다.

```text
riskScore = 0.99
confidenceScore = 0.50
```

실제로 위반이라면 피해가 매우 클 수 있지만, AI 판단이 맞는지는 확실하지 않다는 의미다. 두 점수의 평균은 `0.745`지만 평균값만으로는 중요한 정보가 사라진다.

반대 사례도 가능하다.

```text
riskScore = 0.40
confidenceScore = 0.98
```

가벼운 욕설임은 확실하지만 자동 차단할 만큼 피해가 크지 않다는 의미다.

따라서 자동 처리는 두 점수가 각각 정해진 기준을 모두 통과할 때만 허용해야 한다.

## 5. 최종 판단 구조

정확도와 설명 가능성을 높이기 위해 다음과 같은 3단계 구조를 사용한다.

```text
1. 서버가 객관적 증거 추출
          ↓
2. AI가 의미와 문맥 해석
          ↓
3. 정책 엔진이 최종 조치 결정
```

AI가 직접 DB 상태를 변경하거나 단독으로 처벌을 결정하지 않는다.

### 5.1 서버의 역할: 사실 확인

서버는 AI가 추측해서는 안 되는 객관적인 값을 계산한다.

- URL 포함 여부
- URL 도메인과 허용·주의·차단 목록
- 같은 문구가 게시된 횟수
- 일정 시간 내 게시 빈도
- 여러 게시판에 같은 링크를 올렸는지
- 게시물 간 문자열·의미 유사도
- 전화번호·이메일·주민등록번호·계좌 형태
- 특정 공격 대상 표현 존재 여부
- 글 작성자와 언급된 사용자의 관계 정보 중 정책상 허용된 최소 범위
- 인용 표시 또는 신고 양식에서 전달된 피해 증거 여부
- 게시판 주제와 콘텐츠의 관련성
- 이미 숨김·삭제된 대상인지

예를 들어 AI에게 “도배인지 알아서 판단하라”고 요구해서는 안 된다. AI는 사용자가 몇 분 동안 몇 번 게시했는지 알 수 없으므로 서버가 실제 횟수와 시간 구간을 제공해야 한다.

### 5.2 AI의 역할: 의미와 문맥 해석

AI는 단순 문자열 검색으로 처리하기 어려운 부분을 담당한다.

- `타임특가`, `오늘만`, `한정 수량`이 구매 유도 표현인지
- 정상적인 식당 정보 공유인지 무관한 상업 광고인지
- 욕설이 특정인을 공격하는 직접 발언인지 다른 사람의 발언을 인용한 것인지
- 성적 표현이 성희롱인지 피해 사실을 설명하는 문장인지
- 서비스 비판인지 특정인을 향한 인격 비하인지
- 은어, 초성, 철자 변형을 사용한 우회 욕설인지
- 농담, 풍자, 친근한 표현일 가능성이 있는지
- 여러 유형 중 어떤 위반이 핵심인지
- 판단에 필요한 문맥이 부족한지

### 5.3 정책 엔진의 역할: 최종 통제

정책 엔진은 AI 결과를 신뢰하기 전에 다음을 검증한다.

- AI 응답 JSON이 스키마에 맞는가?
- 허용된 enum과 정책 코드만 사용했는가?
- 위험도와 확실성 범위가 정상인가?
- 유형별 자동 처리 허용 여부를 만족하는가?
- 서버의 객관적인 증거와 AI 판단이 일치하는가?
- 인용·교육·신고 문맥 같은 자동 처리 금지 조건이 없는가?
- 대상이 현재 노출 상태인가?
- 다른 관리자 또는 AI가 이미 처리하지 않았는가?
- 자동 처리 kill switch가 활성화되어 있는가?

AI가 `AUTO_HIDE`를 반환해도 서버 조건을 만족하지 못하면 `REVIEW_REQUIRED`로 낮춘다.

## 6. 유형별 구체화 방향

### 6.1 광고·스팸 `SPAM_AD`

AI가 판단할 의미적 단서:

- 구매·가입·방문·클릭 유도
- 가격 혜택과 긴급성 강조
- 과장된 수익·당첨·무료 제공 약속
- 서비스 주제와 무관한 상업 홍보
- 외부 메신저나 사이트로 이동 유도

서버가 확인할 증거:

- URL 또는 연락처
- 동일 링크·문구 반복 횟수
- 게시 시간 간격
- 여러 게시판 확산 여부
- 피싱·악성 도메인 목록
- 게시판 주제와의 관련성

판단 예:

| 상황 | risk | confidence | 처리 |
|---|---:|---:|---|
| 정상적인 식당 정보 공유 | 낮음 | 높음 | `NO_ACTION` |
| 단일 상업 홍보 문구와 정상 쇼핑몰 링크 | 중간 | 높음 | 관리자 검토 |
| 동일 광고를 여러 번 게시 | 높음 | 높음 | 자동 블라인드 후보 |
| 피싱·사기성 링크와 금전 유도 | 매우 높음 | 높음 | 자동 블라인드 후보 |
| URL만 있고 목적이 불명확 | 낮음~중간 | 낮음 | 관리자 검토 |

### 6.2 개인정보 `PERSONAL_INFO`

AI가 판단할 부분:

- 타인의 정보를 공개하는 문맥인지
- 특정인을 공격하거나 신상을 퍼뜨리려는 문맥인지
- 사업체 공개 정보인지 개인 정보인지
- 피해 신고를 위해 이미 마스킹된 정보인지

서버가 확인할 증거:

- 주민등록번호, 전화번호, 이메일, 계좌, 주소 패턴
- 정보 유형
- 공개 사업체 정보와 일치하는지
- 마스킹 여부

판단 예:

| 상황 | 처리 |
|---|---|
| 주민등록번호·계좌·상세 주소 공개 | 높은 임계값 충족 시 자동 블라인드 |
| “이 사람 번호는…” 형태의 타인 신상 공개 | 관리자 우선 검토 또는 고신뢰 자동 블라인드 |
| 본인의 연락처 게시 가능성 | 관리자 검토 |
| 식당 대표 전화번호와 주소 | `NO_ACTION` 가능 |
| 숫자열의 의미가 불명확 | 관리자 검토 |

### 6.3 도배 `FLOODING`

AI는 문구가 실질적으로 같은 의미인지 보조 판단할 수 있지만, 도배를 확정하는 핵심은 서버 통계다.

필수 증거:

- 설정된 시간 구간
- 동일 또는 유사 콘텐츠 횟수
- 게시 위치 수
- 서비스 이용 방해 정도

단일 게시물 안에 같은 단어가 세 번 반복됐다는 이유만으로 실제 도배를 확정하면 안 된다. 노래 가사, 강조, 장난 등 정상 문맥이 있을 수 있기 때문이다.

### 6.4 일반 욕설 `ABUSE`

판단 요소:

- 특정 대상 존재 여부
- 직접 공격인지 감탄사인지
- 표현 강도
- 반복성
- 혐오·차별 표현 여부
- 인용, 설명, 농담, 피해 신고 가능성

일반적인 불쾌 표현은 AI가 확실하게 욕설로 판단해도 위험도가 자동 처리 기준보다 낮을 수 있으므로 관리자 검토 대상으로 유지한다.

### 6.5 고강도 욕설 `SEVERE_ABUSE`

자동 블라인드 후보가 되려면 다음이 모두 필요하다.

- 식별 가능한 특정 대상
- 명백한 고강도 욕설 또는 심각한 인격 비하
- 작성자가 직접 사용한 표현
- 반대 해석 가능성이 사실상 없음
- 인용·설명·교육·장난·피해 신고가 아님
- 충분한 앞뒤 문맥
- 서버 대상성 규칙과 고강도 표현 규칙 일치
- `riskScore >= 0.95`
- `confidenceScore >= 0.95`

한 조건이라도 부족하면 일반 `ABUSE`와 `REVIEW_REQUIRED`로 낮춘다.

### 6.6 비방·명예훼손 의심 `DEFAMATION`

AI는 타인의 평판을 훼손할 가능성이 있는 주장인지 분류할 수 있다. 그러나 다음은 AI가 확정할 수 없다.

- 주장이 사실인지
- 공익 목적이 있는지
- 법률상 명예훼손에 해당하는지
- 실제 피해가 발생했는지

따라서 이 유형은 점수가 높아도 자동 처리하지 않고 관리자 검토로 보낸다.

### 6.7 성희롱 `SEXUAL_HARASSMENT`

AI는 성적 대상화, 원치 않는 요구, 반복 접근, 성적 위협을 분류할 수 있다. 그러나 관계, 동의, 인용, 피해 신고 여부처럼 중요한 문맥이 필요하다.

명백한 고위험 사례는 관리자 긴급 검토 순위를 높일 수 있지만 초기 자동 블라인드 대상에서는 제외한다.

## 7. 애매함을 판단하는 기준

“AI가 애매하다고 느낀다”는 주관적인 표현만으로는 운영 기준이 될 수 없다. 다음 조건 중 하나라도 존재하면 애매한 사례로 정의한다.

### 7.1 문맥 부족

- 문장이 중간에서 잘림
- 앞뒤 대화가 없음
- 특정 대상이 누구인지 알 수 없음
- 작성자와 상대방의 관계를 알 수 없음
- 신고자가 선택한 사유만 있고 본문 근거가 없음

### 7.2 복수 해석 가능

- 광고와 정상 정보 공유로 모두 해석 가능
- 욕설과 친근한 장난으로 모두 해석 가능
- 성희롱과 피해 설명으로 모두 해석 가능
- 개인정보와 공개 사업 정보로 모두 해석 가능
- 비방과 정당한 소비자 비판으로 모두 해석 가능

### 7.3 인용·설명 가능성

- 다른 사람이 한 말을 전달함
- 욕설의 의미를 설명함
- 교육·연구·상담 문맥
- 받은 피해 내용을 신고함
- 뉴스·문학·콘텐츠의 문장을 인용함

### 7.4 AI와 서버 증거 불일치

- AI는 도배라고 판단했지만 반복 기록이 없음
- AI는 개인정보라고 판단했지만 유효한 패턴이 없음
- AI는 광고라고 판단했지만 URL·구매 유도·반복 증거가 없음
- AI는 고강도 욕설이라고 판단했지만 대상이 불명확함

### 7.5 정책 경계값

- risk 또는 confidence가 자동 처리 임계값 바로 아래에 있음
- 여러 유형의 점수가 비슷함
- 필수 정책 코드가 누락됨
- 새로운 은어·표현이라 검증 데이터에 유사 사례가 없음

### 7.6 기술적 불확실성

- AI 응답 일부가 잘림
- 안전 필터가 입력을 차단함
- JSON 의미 검증 실패
- 모델 재시도마다 유형이 달라짐
- 대상 콘텐츠가 분석 도중 수정·삭제됨

이러한 사례는 위험도가 높더라도 자동 처리하지 않는다. 위험도가 높고 확실성이 낮다면 오히려 관리자 긴급 검토 우선순위를 높인다.

---

## 8. 점수 조합별 처리 기준

| riskScore | confidenceScore | 의미 | 기본 처리 |
|---|---|---|---|
| 낮음 | 높음 | 위반이 아니거나 피해가 작다는 판단이 확실 | `NO_ACTION` |
| 낮음 | 낮음 | 정보 부족으로 판단 자체가 어려움 | 관리자 검토 또는 추가 정보 요청 |
| 중간 | 높음 | 위반 유형은 확실하지만 자동 차단할 정도는 아님 | 관리자 검토 |
| 높음 | 낮음 | 실제 위반이면 피해가 크지만 오판 가능성 존재 | 관리자 긴급 검토 |
| 높음 | 높음 | 위반과 피해가 모두 명확 | 자동 허용 유형에 한해 자동 블라인드 |
| 임계값 근처 | 무관 | 정책 경계에 위치 | 관리자 검토 |

자동 처리에는 평균이나 합산 점수를 사용하지 않는다.

예시:

```text
일반 자동 처리:
riskScore >= 0.90 AND confidenceScore >= 0.90

SEVERE_ABUSE:
riskScore >= 0.95 AND confidenceScore >= 0.95
```

점수 외에도 유형별 필수 증거를 모두 만족해야 한다.

## 9. AI 응답에 추가할 설명 근거

관리자가 판단을 납득할 수 있도록 AI는 결론뿐 아니라 근거를 구조적으로 반환해야 한다.

권장 확장 응답:

```json
{
  "category": "SPAM_AD",
  "decision": "REVIEW_REQUIRED",
  "riskScore": 0.65,
  "confidenceScore": 0.94,
  "policyCodes": ["SPAM-COMMERCIAL"],
  "evidence": [
    {
      "type": "URGENCY_EXPRESSION",
      "maskedText": "오늘만 이 가격"
    },
    {
      "type": "EXTERNAL_URL",
      "maskedText": "https://www.m***.com"
    }
  ],
  "alternativeCategory": "SAFE",
  "alternativeReason": "허용된 정보 공유일 가능성은 있으나 구매 유도 표현이 더 명확합니다.",
  "missingContext": ["반복 게시 횟수", "게시판 주제와의 관련성"],
  "reasonSummary": "가격 혜택과 시간 제한을 강조하며 외부 상업 사이트 방문을 유도합니다."
}
```

운영 원칙:

- 근거는 실제 입력에 존재하는 내용만 사용
- 입력에 없던 사실을 생성하지 않음
- 개인정보와 심한 욕설은 관리자 화면에서도 필요한 범위만 마스킹
- 대안 해석과 부족한 문맥을 함께 표시
- “위반입니다”라는 결론보다 어떤 정책 코드와 증거가 적용됐는지 표시

## 10. confidenceScore를 그대로 믿으면 안 되는 이유

LLM이 출력한 `confidenceScore=0.97`이 실제 정확도 97%를 의미하지는 않는다. 모델은 자신의 확실성을 과대평가하거나 사례에 따라 일관되지 않게 표현할 수 있다.

신뢰 가능한 confidence는 다음 요소를 조합해 보정해야 한다.

- AI와 서버 규칙이 일치하는지
- 근거 문장이 명확한지
- 필요한 문맥이 모두 제공됐는지
- 정상적인 대안 해석이 존재하는지
- 동일 입력을 다시 평가했을 때 결과가 일관되는지
- 검증 데이터에서 해당 유형의 실제 정답률이 얼마인지
- 새로운 표현이 기존 검증 사례와 얼마나 다른지

장기적으로는 다음 두 값을 분리하는 것이 적절하다.

- `modelConfidence`: 모델이 반환한 원점수
- `calibratedConfidence`: 검증 데이터와 서버 증거를 이용해 보정한 운영 점수

자동 처리에는 `calibratedConfidence`를 사용한다.

## 11. 실제 정확도 검증 계획

### 11.1 검증 데이터 구성

한국어 신고 데이터셋에는 다음 사례가 포함되어야 한다.

- 명백한 정책 위반
- 정상적인 문장
- 위반과 정상의 경계 사례
- 초성·은어·철자 변형 욕설
- 인용·교육·피해 신고 문장
- 상업 광고와 정상적인 정보 공유
- 공개 사업체 정보와 개인 연락처
- 풍자·농담·친근한 대화
- 사실을 확인할 수 없는 비방
- 성적 표현이 포함된 교육·피해 문맥
- 짧은 시간의 실제 반복 게시 데이터
- 프롬프트 인젝션 문구
- 오탈자, 띄어쓰기 제거, 특수문자 우회

초기에는 최소 수백 건을 구성하고 자동 처리 대상 유형은 더 많은 경계 사례를 확보한다.

### 11.2 라벨링 방식

- 최소 2명이 각 사례를 독립적으로 판단
- 유형, 위험도 구간, 자동 처리 가능 여부를 각각 기록
- 두 판단자가 불일치한 사례는 자동 처리 학습 기준으로 사용하지 않고 경계 사례로 분리
- 개인정보는 마스킹된 가상 데이터 사용
- 단순 다수결보다 불일치 이유를 정책 문서에 반영

### 11.3 측정 지표

- `precision`: AI가 자동 처리한 것 중 실제 위반인 비율
- `recall`: 실제 위반 중 AI가 찾아낸 비율
- `false positive rate`: 정상 콘텐츠를 위반으로 처리한 비율
- 관리자 복구율: 자동 처리 중 관리자가 되돌린 비율
- 유형 정정률: AI가 선택한 유형을 관리자가 바꾼 비율
- 검토 전환율: 애매한 사례를 관리자에게 보낸 비율
- JSON 검증 성공률
- 평균 분석 시간과 실패율

자동 블라인드에서는 recall보다 precision을 우선한다. 위반을 일부 관리자 검토로 보내더라도 정상 콘텐츠를 자동 차단하는 오탐을 줄이는 것이 중요하다.

### 11.4 권장 목표

- 전체 자동 블라인드 precision: 최소 97~98%
- 개인정보·SEVERE_ABUSE precision: 99%에 가까운 목표
- 관리자 복구율: 2% 이하
- JSON 검증 성공률: 99% 이상
- AI 장애 시 신고 접수 성공률: 100%
- 자동 처리된 모든 건의 처리 전 상태와 근거 보존율: 100%

위 수치는 실제 검증 데이터 결과를 보고 조정해야 한다. 단순히 모델이 높은 점수를 반환했다는 이유로 달성했다고 간주하지 않는다.

## 12. 단계별 고도화 계획

### 1단계: Mock 흐름 검증

- 신고 접수부터 분석 저장까지 검증
- 자동 블라인드와 복구 검증
- 관리자 상세 근거 표시
- 트랜잭션과 처리 이력 검증
- 실패 로그와 fallback 검증

현재 단계에 해당한다.

### 2단계: Mock 규칙 보완

- 공모전 데모에 필요한 대표적인 광고·개인정보·도배·욕설 표현 추가
- 키워드 하나가 아니라 단서 조합으로 판단
- 정상 문장과 경계 문장의 fixture 추가
- Mock 점수는 실제 신뢰도가 아니라 시나리오 값임을 명시

이 단계는 데모 품질을 높이지만 실제 AI 의미 추론을 대체하지 않는다.

### 3단계: Gemini shadow mode

- 실제 Gemini가 분석하지만 자동 블라인드는 실행하지 않음
- AI 결과와 관리자 판단을 비교
- 유형별 오탐과 누락 수집
- 프롬프트, 스키마, 정책 코드 개선
- 모델 안전 필터와 timeout 사례 수집

### 4단계: 점수 보정

- 검증 데이터에서 유형별 precision·recall 측정
- 모델 confidence와 실제 정답률 비교
- 유형별 임계값 별도 설정
- 서버 증거 일치 여부를 반영한 `calibratedConfidence` 계산
- 경계 구간 정의

### 5단계: 제한적 자동 처리

- precision이 목표를 충족한 유형만 활성화
- 광고·도배·명백한 개인정보부터 시작
- 카테고리별 feature flag 제공
- 자동 처리 수량과 복구율 실시간 모니터링
- 이상 시 kill switch로 즉시 자동 처리 중단

### 6단계: 피드백 운영

- 관리자 복구·유형 정정을 평가 데이터 후보로 축적
- 검수되지 않은 관리자 판단을 즉시 모델 학습에 사용하지 않음
- 정책 버전별 성능 비교
- 새 은어·광고 패턴·우회 표현을 정기적으로 추가
- 과거 데이터를 새 정책으로 소급 자동 처리하지 않음

## 13. 관리자 화면에서 제공할 정보

관리자는 다음 내용을 한 화면에서 확인할 수 있어야 한다.

- AI가 선택한 신고 유형
- riskScore와 의미
- modelConfidence와 보정 confidence
- 서버 보조 규칙 일치 여부
- 적용된 정책 코드
- 마스킹된 핵심 근거
- 가능한 대안 해석
- 부족한 문맥
- 자동 처리 또는 관리자 검토가 된 이유
- 처리 전후 대상 상태
- 모델명과 정책 버전
- 복구 버튼과 복구 사유 입력

예시:

```text
AI 판단: 광고/스팸
위험도: 0.65 — 단일 상업 홍보로 피해 가능성은 중간
판단 확실성: 0.94 — 시간 제한, 가격 혜택, 외부 URL이 명확
서버 증거: URL 확인, 반복 게시 기록 없음
최종 처리: 관리자 검토
처리 이유: 광고 유형은 확실하지만 자동 블라인드 위험도 기준에 미달
```

이와 같은 설명이 있어야 관리자가 점수만 보고 추측하지 않아도 된다.

## 14. 공모전 발표 시 신뢰성 표현

현재 Mock 단계에서 다음과 같이 말하면 안 된다.

> AI가 97% 확률로 정확하게 광고를 판단했습니다.

현재 점수는 검증 데이터로 보정한 확률이 아니기 때문이다.

현재 단계의 정확한 설명:

> Mock 단계에서는 AI 자동 처리에 필요한 신고 접수, 정책 검증, 가역적 블라인드, 감사 이력, 관리자 복구 흐름을 검증했습니다.

실제 Gemini 검증 이후 목표 설명:

> AI의 의미 분석 결과를 서버의 반복 횟수, 개인정보 패턴, URL 정보와 결합하고, 실제 한국어 검증 데이터에서 목표 precision을 충족한 유형만 자동 처리합니다. 애매한 사례는 관리자가 검토하며 모든 자동 처리는 복구할 수 있습니다.

공모전에서 강조할 신뢰성 포인트:

1. AI가 단독으로 처벌하지 않음
2. 의미 판단과 객관적 증거를 결합
3. 위험도와 판단 확실성을 분리
4. 유형별로 서로 다른 자동 처리 기준 적용
5. 애매함을 구체적인 조건으로 정의
6. 영구 삭제와 계정 제재를 자동화하지 않음
7. 처리 전 상태를 저장해 즉시 복구 가능
8. 관리자 정정을 통해 성능을 측정하고 개선
9. 실제 precision과 복구율로 신뢰도를 증명
10. 장애가 발생해도 신고 접수와 관리자 검토는 유지

---

## 15. 현재 정책의 신뢰도 평가

현재 구조의 방향은 신뢰할 수 있다.

- `riskScore`와 `confidenceScore`를 분리함
- 자동 허용 유형과 자동 금지 유형을 구분함
- 서버 보조 규칙을 함께 검증함
- 자동 처리를 가역적 블라인드로 제한함
- 처리 전 상태와 처리 주체를 기록함
- 관리자가 사후 확인하고 복구할 수 있음
- AI 장애가 신고 접수를 취소하지 않음

그러나 현재 Mock의 분류 정확도와 점수 자체는 아직 신뢰도 검증이 되지 않았다.

- 제한된 키워드만 인식함
- 문맥을 실제로 이해하지 못함
- 점수가 고정된 시나리오 값임
- 한국어 검증 데이터로 보정되지 않음
- 유형별 오탐률과 누락률이 측정되지 않음

따라서 현재 기능은 “신뢰할 수 있는 자동화 구조를 구현한 단계”이지 “신뢰도가 입증된 AI 모델을 완성한 단계”는 아니다.

신뢰도는 다음 순서로 확보한다.

```text
정책을 명확히 정의
→ 실제 한국어 경계 데이터 확보
→ AI와 관리자 판단 비교
→ 유형별 점수 보정
→ 목표 precision 충족 확인
→ 제한적 자동 처리 활성화
→ 관리자 복구율로 지속 검증
```

최종적으로 납득할 수 있는 AI 신고 시스템은 높은 점수를 보여주는 시스템이 아니라, **왜 그렇게 판단했는지 설명할 수 있고, 오판 가능성을 측정하며, 애매한 사례를 사람에게 넘기고, 잘못된 조치를 즉시 복구할 수 있는 시스템**이다.
